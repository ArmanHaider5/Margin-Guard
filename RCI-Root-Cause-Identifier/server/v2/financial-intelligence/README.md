## What this module consumes

**Only `StructuredDocument` and `EvidenceObject`** — `document-parser/`'s public output (per ADR-009 and `server/v2/README.md`'s dependency table). This module has no import of, and no dependency on, any `document-parser/` internal type (`DocumentModel`, `RawContent`, `UploadedFile`) or any parsing library. It does not care whether the source document was Excel, PDF, Word, or CSV.

**Target architecture** (per the layered pipeline this module is being built toward):

```
StructuredDocument
  ↓
EvidenceObject[]
  ↓
Financial Objects (internal)
  ↓
Financial Metrics
  ↓
Financial Ratios
  ↓
Financial Observations
  ↓
Financial Evidence
  ↓
Financial Signals
```

**Current implementation status — stated honestly, not rounded up.** `MetricCalculator`/`RatioCalculator`/`ObservationCalculator` now have **real implementations for the liquidity and profitability domains** (`capabilities/liquidity/`, `capabilities/profitability/`) — 7 of 15 metrics, 4 of 12 ratios, 4 of 11 observations. Every other registered definition still has no calculator — calling `DefaultFinancialCalculationPipeline` with the *default* (empty) calculator arrays still returns empty results for those, exactly as before.

`analyzeFinancialSignals()`, the module's public entry point, is **unchanged and still does not use any of this**:

```
StructuredDocument + EvidenceObject[]
  ↓  FinancialEvidenceClassifier
FinancialEvidence[]
  ↓  FinancialSignalGenerator
FinancialSignal[]
```

It has **not** been rewired through the Metric/Ratio/Observation layer. Each Capability Pack's own entry point (`runLiquidityCapabilityPack`, `runProfitabilityCapabilityPack`, `runCashFlowCapabilityPack`, `runWorkingCapitalCapabilityPack`, same `(document, evidence)` signature as `analyzeFinancialSignals`) is where the full target pipeline — Financial Objects → Metrics → Ratios → Observations → Evidence → Signals — actually runs end to end, one domain at a time. See "Capability Packs" below.

## Financial Object Model (internal)

`models/financial-object-model.ts` defines the fourteen internal types from [`05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md`](../../../docs/05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md) Chapter 4 (Financial Account, Account Group, Ledger Entry, Posting, Balance, Variance, Working Capital Component, Cash Movement, Asset, Liability, Equity, Revenue, Expense). **Internal to this module**, exactly as `DocumentModel` is internal to `document-parser/` (ADR-009) — never exported from `index.ts`, never consumed by another module.

`Asset`/`Liability` gained real construction logic in the Liquidity Capability Pack milestone (`capabilities/liquidity/current-asset-liability-builder.ts`); `Revenue`/`Expense` gained it in the Profitability Capability Pack milestone (`capabilities/profitability/revenue-expense-builder.ts`); `CashMovement` gained it in the Cash Flow Capability Pack milestone (`capabilities/cash-flow/cash-movement-builder.ts`); `WorkingCapitalComponent` gained it in the Working Capital Capability Pack milestone (`capabilities/working-capital/working-capital-component-builder.ts`); `Equity` gained it, and `Liability`'s `"non_current"` classification was constructed for real for the first time, in the Leverage Capability Pack milestone (`capabilities/leverage/leverage-object-builder.ts`); `Asset`'s `"non_current"` classification was constructed for real for the first time in the Efficiency Capability Pack milestone (`capabilities/efficiency/non-current-asset-builder.ts`), mirroring Leverage's non-current-Liability builder exactly, applied to Assets instead. All six types gained `id`, `confidence`, and `evidenceObjectIds` fields to support this (`CashMovement.evidenceObjectId` was renamed from a single string to the array form for consistency; `period`/`date` were loosened from required to optional — no reliable period/date-boundary detection exists yet); `Asset`/`Liability` also gained `classification: "current" | "non_current"`, and `Expense` gained `category?: "cogs" | "operating"`. `Revenue` gained `periodSequence?: "prior" | "current"` during the Growth Capability Pack milestone (`capabilities/growth/period-revenue-builder.ts`) — the same "add one distinguishing field" pattern, populated only by Growth's own builder, which tags the last two rows of a Revenue-normalized column (in row order) as a disclosed proxy for consecutive periods (no real `Period`/date-boundary value is constructed; see `docs/98_TECHNICAL_BACKLOG.md` GR-001). `AccountGroup`, `FinancialAccount`, `LedgerEntry`, `Posting`, `Balance`, and `Variance` remain unpopulated until their own capability packs are built.

## Financial Metrics

`shared/contracts/financial-metric.ts` defines the public `FinancialMetric` instance type (a computed quantity for one document/period, e.g. "Total Revenue: 50000, Q1 2026") and its `FinancialMetricUnit` (`currency | count | percentage | days`). **Public**, unlike the Financial Object Model — per [`MGD_V2_BLUEPRINT.md`](../../../docs/MGD_V2_BLUEPRINT.md) §9.2 and [`05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md`](../../../docs/05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md) §11.2, Financial Metrics and Ratios are explicitly intended for future cross-module reuse (e.g. a future YieldIQ integration), unlike the Financial Object Model's purely internal working representation.

`metrics/financial-metric-definitions.ts` defines `FinancialMetricDefinition` (internal — the knowledge-level metadata: id, name, description, unit, Ontology reference where applicable, and which Financial Object Model types conceptually feed it) and `FinancialMetricRegistry`, seeded via `createDefaultFinancialMetricRegistry()` with **twenty** built-in definitions grounded in the Financial Object Model: `total_revenue`, `total_expense`, `gross_profit`, `cost_of_goods_sold`, `total_operating_expenses`, `net_profit`, `total_current_assets`, `total_current_liabilities`, `total_assets`, `total_liabilities`, `total_equity`, `accounts_receivable_balance`, `accounts_payable_balance`, `inventory_balance`, `net_cash_flow`, `cash_generated`, `cash_used`, `operating_cash_flow`, `current_period_revenue`, `prior_period_revenue`. **Nineteen of twenty now have a real calculator** — `total_liabilities`/`total_equity` were populated by the Leverage milestone; `total_assets` was populated by the Efficiency milestone; `current_period_revenue`/`prior_period_revenue` are new definitions the Growth milestone introduced *and* immediately populated (the **first** new Metric definitions any pack has added — see `docs/98_TECHNICAL_BACKLOG.md` GR-002). **Correction to this README's own prior revision**: the Leverage milestone's version of this section stated "all eighteen now have a real calculator," which was factually wrong — verified false via a direct grep of every `capabilities/*/*.ts` file for `definitionId`/`readonly definition` declarations, which showed `total_expense` and `total_assets` both had none at that point. `total_assets` was fixed by the Efficiency milestone; `total_expense` still has no calculator — no Capability Pack built so far needs a *combined* Revenue-and-COGS-and-OpEx total (Profitability's own Metrics use `cost_of_goods_sold` and `total_operating_expenses` separately).

`metrics/metric-calculator.ts` defines the `MetricCalculator` interface (internal) — the contract a calculation service implements per definition, consuming a `FinancialObjectSet` and producing a `FinancialMetric`. **Nineteen real implementations exist**: `capabilities/liquidity/`'s `TotalCurrentAssetsCalculator`/`TotalCurrentLiabilitiesCalculator`; `capabilities/profitability/profitability-metric-calculators.ts`'s `TotalRevenueCalculator`/`CostOfGoodsSoldCalculator`/`GrossProfitCalculator`/`TotalOperatingExpensesCalculator`/`NetProfitCalculator`; `capabilities/cash-flow/cash-flow-metric-calculators.ts`'s `CashGeneratedCalculator`/`CashUsedCalculator`/`OperatingCashFlowCalculator`/`NetCashFlowCalculator`; `capabilities/working-capital/working-capital-metric-calculators.ts`'s `AccountsReceivableBalanceCalculator`/`AccountsPayableBalanceCalculator`/`InventoryBalanceCalculator`; `capabilities/leverage/leverage-metric-calculators.ts`'s `TotalLiabilitiesCalculator`/`TotalEquityCalculator`; `capabilities/efficiency/total-assets-calculator.ts`'s `TotalAssetsCalculator`; `capabilities/growth/growth-metric-calculators.ts`'s `CurrentPeriodRevenueCalculator`/`PriorPeriodRevenueCalculator`. Every calculator reads directly from `context.financialObjects`, never from another calculator's already-computed output — `MetricCalculationContext` deliberately has no visibility into sibling calculators, so e.g. `NetProfitCalculator`/`NetCashFlowCalculator` independently re-derive their result from raw Financial Objects rather than subtracting another already-computed Metric (mathematically equivalent, computed separately by design). `TotalLiabilitiesCalculator` and `TotalAssetsCalculator` both sum their respective `context.financialObjects` array **without** filtering by `classification` — the "sum-all-regardless-of-classification" shape, documented but not yet abstracted (see `docs/98_TECHNICAL_BACKLOG.md` EFF-003) — each trusts its caller (the Leverage/Efficiency orchestrator respectively) to have already merged the `"current"`-classified entries reused from Liquidity with its own `"non_current"`-classified ones into one array before calling it. `CurrentPeriodRevenueCalculator`/`PriorPeriodRevenueCalculator` instead filter `context.financialObjects.revenue` by the new `periodSequence` tag — the same "filter one shared array by a distinguishing field" shape Profitability's `cogsOf`/`operatingExpensesOf` helpers already established for `Expense.category`. One registered definition — `total_expense` — still lacks a calculator. **The Investment Capability Pack added zero new Metric definitions and zero new calculators** — its Ratio needs only `gross_profit` and `total_equity`, both already fully computed by `GrossProfitCalculator` (Profitability) and `TotalEquityCalculator` (Leverage), reused directly and unmodified.

## Financial Ratios

`shared/contracts/financial-ratio.ts` defines the public `FinancialRatio` instance type and its `FinancialRatioCategory` — the eleven categories from [`05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md`](../../../docs/05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md) Chapter 7.

`ratios/financial-ratio-definitions.ts` defines `FinancialRatioDefinition` (internal) and `FinancialRatioRegistry`, seeded via `createDefaultFinancialRatioRegistry()` with **thirteen** built-in definitions covering ten of the eleven categories: `current_ratio` (liquidity), `gross_margin`/`net_margin`/`operating_margin` (profitability), `asset_turnover` (efficiency), `debt_to_equity` (leverage), `days_inventory_outstanding` (activity), `operating_cash_flow_ratio`/`cash_coverage_ratio` (cash_flow), `revenue_growth_rate` (growth), `working_capital_ratio` (working_capital), `return_on_assets` (return), `return_on_equity` (investment). **`operational`** (the boundary category — ratios combining financial and operational data, e.g. revenue per employee) is **deliberately unpopulated**: it requires data from `operational-intelligence/`, which does not exist yet, and this module must never depend on it directly (per `server/v2/README.md`'s "no lateral dependencies between domain modules" rule) — that category becomes real only once `correlation/` exists to combine the two modules.

`ratios/ratio-calculator.ts` defines the `RatioCalculator` interface (internal) — mirrors `metric-calculator.ts`. **Eleven real implementations exist**: `capabilities/liquidity/current-ratio-calculator.ts`'s `CurrentRatioCalculator`; `capabilities/profitability/profitability-ratio-calculators.ts`'s `GrossMarginCalculator`/`NetMarginCalculator`/`OperatingMarginCalculator`; `capabilities/cash-flow/cash-flow-ratio-calculators.ts`'s `OperatingCashFlowRatioCalculator`/`CashCoverageRatioCalculator`; `capabilities/working-capital/working-capital-ratio-calculator.ts`'s `WorkingCapitalRatioCalculator`; `capabilities/leverage/debt-to-equity-calculator.ts`'s `DebtToEquityCalculator` (total_liabilities ÷ total_equity — a single, universally-standard formula, unlike Cash Coverage Ratio's disclosed multi-definition choice); `capabilities/efficiency/asset-turnover-calculator.ts`'s `AssetTurnoverCalculator` (total_revenue ÷ total_assets — likewise a single, universally-standard formula); `capabilities/growth/revenue-growth-rate-calculator.ts`'s `RevenueGrowthRateCalculator` ((current_period_revenue − prior_period_revenue) ÷ prior_period_revenue); `capabilities/investment/return-on-equity-calculator.ts`'s `ReturnOnEquityCalculator` (gross_profit ÷ total_equity — the `investment` category's first coverage). All eleven guard against division by zero. `NetMarginCalculator`/`OperatingMarginCalculator` currently compute an identical value (see `docs/98_TECHNICAL_BACKLOG.md` PC-002). `AssetTurnoverCalculator` draws its two Metrics from two different other packs at once (`total_revenue` reused from Profitability, `total_assets` computed by Efficiency's own `TotalAssetsCalculator`, which itself reuses Liquidity's current-Asset construction) — see "Cross-pack Metric reuse" below. `RevenueGrowthRateCalculator` is the **first** Ratio calculator that does **not** reuse another pack's Metric at all — both of its inputs are Growth's own new Metrics, since no existing Metric represents a single period's Revenue in isolation (a disclosed, honest exception to "reuse whenever possible," not a missed reuse opportunity — see `docs/98_TECHNICAL_BACKLOG.md` GR-002). `revenue_growth_rate`'s own `requiredMetricDefinitionIds` was also updated this milestone from its Sprint 2 Foundation placeholder — see `docs/98_TECHNICAL_BACKLOG.md` GR-002 for the full disclosure. `ReturnOnEquityCalculator` reuses both of its Metrics from two different other packs at once, same as `AssetTurnoverCalculator` — `gross_profit` from Profitability's `GrossProfitCalculator`, `total_equity` from Leverage's `TotalEquityCalculator`, both called directly and unmodified. The remaining two registered definitions still have no calculator.

## Financial Observations

`shared/contracts/financial-observation.ts` defines the public `FinancialObservation` instance type — an **objective, non-diagnostic statement of business fact** derived from one or more `FinancialMetric`/`FinancialRatio` instances, e.g. "Current ratio is below the preferred operating range." An Observation states *what* was observed; it never concludes, diagnoses, or assigns cause — that distinction is structural, not stylistic, and is what separates this stage from Financial Evidence and, further downstream, from `brain/`'s exclusive right to construct conclusion-shaped objects (ADR-006). `FinancialObservationCategory` reuses `FinancialRatioCategory`'s eleven domain categories rather than introducing a second, parallel taxonomy — an Observation belongs to the same business domain as its underlying Metric(s)/Ratio(s). **Public**, for the same reason `FinancialMetric`/`FinancialRatio` are (see that section above).

`observations/financial-observation-definitions.ts` defines `FinancialObservationDefinition` (internal — id, name, description, category, a fixed `statementTemplate` in plain business language, and which Metric/Ratio definitions it is conceptually derived from) and `FinancialObservationRegistry`, seeded via `createDefaultFinancialObservationRegistry()` with **eighteen** built-in definitions covering nine of the eleven categories: `current_ratio_below_range` (liquidity), `gross_margin_declined` / `expense_growth_outpaced_revenue` / `gross_margin_negative` / `net_margin_negative` / `operating_margin_negative` (profitability), `operating_cash_flow_negative` / `cash_coverage_ratio_low` (cash_flow), `inventory_turnover_slowing` / `receivable_collection_period_increased` (activity), `leverage_increased` / `debt_to_equity_negative` (leverage), `working_capital_ratio_negative` / `working_capital_weakened` (working_capital), `revenue_growth_slowed` / `revenue_growth_negative` (growth), `asset_turnover_zero` (efficiency), `return_on_equity_negative` (investment). `return` and `operational` have no registered definition yet — an honest partial-coverage gap. `gross_margin_negative`/`net_margin_negative`/`operating_margin_negative`/`operating_cash_flow_negative`/`working_capital_ratio_negative`/`debt_to_equity_negative`/`revenue_growth_negative`/`return_on_equity_negative` (all "below zero") are deliberately distinct conditions from the pre-existing, still-unimplemented trend-based definitions (`gross_margin_declined`, `expense_growth_outpaced_revenue`, `working_capital_weakened`, `leverage_increased`, `revenue_growth_slowed` — see `docs/98_TECHNICAL_BACKLOG.md` PC-003) — a single-period, universally-defensible threshold, unlike a "healthy" percentage, which is industry-dependent. `debt_to_equity_negative` specifically means negative shareholders' equity (total liabilities exceed total assets) — a distinct, severe solvency condition, not merely "unhealthy." `cash_coverage_ratio_low` instead uses a "below 1.0" threshold (see `docs/98_TECHNICAL_BACKLOG.md` CF-002) — also chosen to avoid an industry-dependent guess. `asset_turnover_zero` uses an exact-**zero** condition rather than a low-turnover threshold: unlike Current Ratio's disclosed 1.5 heuristic (LC-002), Asset Turnover has no natural "healthy minimum" that isn't even more industry-dependent (a services business and a capital-intensive manufacturer have structurally different "normal" turnover), so this pack follows the majority "below zero"/"exactly zero" pattern instead of inventing a second arbitrary threshold. `revenue_growth_negative` (Growth milestone) is deliberately distinct from `revenue_growth_slowed` immediately above it in the registry — "negative growth" needs only the two-period comparison Growth's Ratio layer performs, while "growth *slowed*" is a genuine deceleration trend needing a **third** period (comparing one growth rate against an earlier one), still blocked by the same period-tracking gap as every other unimplemented trend definition. `return_on_equity_negative` (Investment milestone) is the `investment` category's first coverage, the same "below zero" pattern as every prior "negative" definition.

`observations/observation-calculator.ts` defines the `ObservationCalculator` interface (internal) — consumes a document's computed `FinancialMetric[]`/`FinancialRatio[]` and produces a `FinancialObservation`. **Eleven real implementations exist**: `capabilities/liquidity/current-ratio-below-range-calculator.ts`'s `CurrentRatioBelowRangeCalculator` (fires when `current_ratio` is below `PREFERRED_CURRENT_RATIO_MINIMUM`, 1.5 — a disclosed industry-standard heuristic pending a real Benchmark object; see `docs/98_TECHNICAL_BACKLOG.md` LC-002); `capabilities/profitability/profitability-observation-calculators.ts`'s `GrossMarginNegativeCalculator`/`NetMarginNegativeCalculator`/`OperatingMarginNegativeCalculator`; `capabilities/cash-flow/cash-flow-observation-calculators.ts`'s `OperatingCashFlowNegativeCalculator`/`CashCoverageRatioLowCalculator`; `capabilities/working-capital/working-capital-observation-calculator.ts`'s `WorkingCapitalRatioNegativeCalculator`; `capabilities/leverage/debt-to-equity-negative-calculator.ts`'s `DebtToEquityNegativeCalculator`; `capabilities/efficiency/asset-turnover-zero-calculator.ts`'s `AssetTurnoverZeroCalculator`; `capabilities/growth/revenue-growth-negative-calculator.ts`'s `RevenueGrowthNegativeCalculator`; `capabilities/investment/return-on-equity-negative-calculator.ts`'s `ReturnOnEquityNegativeCalculator`. The remaining seven registered definitions still have no calculator.

Financial Observations are the **mandatory input to Financial Evidence** for the liquidity, profitability, and cash-flow slices as of this milestone — see "Capability Packs" below for how each pack's entry point realizes this. Other domains' Evidence generation is unchanged (still direct from `EvidenceObject[]`, per `FinancialEvidenceClassifier` below).

## Financial Calculation Pipeline — execution architecture (new this milestone)

**Status: frozen at the same point as the models it orchestrates.** The Financial Intelligence contracts (`FinancialMetric`, `FinancialRatio`, `FinancialObservation`, `FinancialEvidence`, `FinancialSignal`) are frozen as of this milestone — no additional pipeline stage may be introduced without a new ADR. This milestone shifts from *structural* architecture (what the pipeline's stages are) to *execution* architecture (how a stage's calculators actually run, in what order, against what input) — entirely internal to `financial-intelligence/`, adding nothing to `shared/contracts/`.

`pipeline/calculation-stage-order.ts` defines `FINANCIAL_CALCULATION_STAGE_ORDER = ["metric", "ratio", "observation"]` — the fixed, only-permitted execution order, documented as structural rather than a preference: a Ratio can only be computed from already-computed Metrics, and an Observation can only be computed from already-computed Metrics/Ratios.

`pipeline/execution-context.ts` defines `FinancialCalculationExecutionContext` — the single top-level input to a pipeline run (`documentId`, optional `period`, and the internal `FinancialObjectSet`). It seeds Stage 1 only; Stages 2 and 3 never read it directly — their contexts (the existing `RatioCalculationContext`/`ObservationCalculationContext`) are built exclusively from the prior stage(s)' completed output arrays, which is what makes the dependency ordering between calculators structural rather than merely conventional.

Each calculator kind gets its own small, **real** (not interface-only) runner — the "calculator framework" for that stage:
- `metrics/metric-calculation-stage.ts` — `runMetricCalculators(calculators, context)`.
- `ratios/ratio-calculation-stage.ts` — `runRatioCalculators(calculators, context)`.
- `observations/observation-calculation-stage.ts` — `runObservationCalculators(calculators, context)`.

Each runner iterates its calculator array in exact given order (never a `Set`/`Map` iteration), gates every calculator with its own `canCalculate()` before ever calling `calculate()`, and silently skips a calculator that returns `undefined` despite `canCalculate()` returning true (a contract violation of that calculator, not the runner's concern). This is genuinely implemented, tested orchestration logic — it contains no formulas, so implementing it does not violate "do not calculate metrics/ratios/observations."

`pipeline/financial-calculation-pipeline.ts` defines the orchestration interface `FinancialCalculationPipeline` (`run(context): FinancialCalculationResult`) and its one real implementation, `DefaultFinancialCalculationPipeline` — constructed with a fixed, ordered `MetricCalculator[]`/`RatioCalculator[]`/`ObservationCalculator[]` per stage, and running them Metrics → Ratios → Observations exactly as `calculation-stage-order.ts` mandates. `runLiquidityCapabilityPack()` and `runProfitabilityCapabilityPack()` construct their own instance with their own real calculators — proof the shared execution architecture genuinely generalizes across domains. `runCashFlowCapabilityPack()`, `runWorkingCapitalCapabilityPack()`, `runLeverageCapabilityPack()`, `runEfficiencyCapabilityPack()`, `runGrowthCapabilityPack()`, and `runInvestmentCapabilityPack()` instead call `runMetricCalculators`/`runRatioCalculators`/`runObservationCalculators` (the same stage-runner functions `DefaultFinancialCalculationPipeline` itself calls) directly — Cash Flow/Working Capital/Leverage/Efficiency/Investment each need to inject at least one other pack's Metric between the Metric and Ratio stages, a point `DefaultFinancialCalculationPipeline`'s single `run()` call has no hook for; Growth uses the same direct-stage-runner shape purely for consistency, even though (uniquely among these six) it injects no other pack's Metric at all. (Correcting a gap in this README's own prior revision, which named only Cash Flow and Working Capital here despite Leverage having already used the same direct-stage-runner shape.) This orchestration layer is **not called from `analyzeFinancialSignals()`** and is not exported from `index.ts` — every Capability Pack constructs and runs its own pipeline instance (or stage-runner calls) directly.

All of `pipeline/`, plus the three `*-calculation-stage.ts` runner functions, are internal to `financial-intelligence/` — never exported from `index.ts`, per the same reasoning as `MetricCalculator`/`RatioCalculator`/`ObservationCalculator`/the three registries.

## Shared Internals (`internal/capability-support/`, frozen except defect fixes)

Introduced in a dedicated refactoring milestone between Cash Flow and Working Capital — **behaviour-preserving**: the full pre-existing test suite passed unmodified immediately after this extraction, before any Working Capital code was added, confirming zero change in output.

- **`EvidenceChainResolver`** (`evidence-chain-resolver.ts`) — the Observation→Ratio→Metric→FinancialObject→EvidenceObject walk, extracted after it had accumulated as three near-identical private `resolveEvidenceObjectIds()` functions in Liquidity's, Profitability's, and Cash Flow's own evidence generators (deliberately *not* extracted after the first or second occurrence — only once a third confirmed the shape was genuinely stable; see `docs/98_TECHNICAL_BACKLOG.md` PC-004/CF-003 for that history). Generic over `EvidenceLinkedFinancialObject` (`{ id, evidenceObjectIds }`), which every Financial Object Model type already satisfies structurally. Exposes `resolve()` (one Observation) and `resolveMany()` (a set of Observations, unioned — the exact shape every evidence generator needs). Directly unit-tested (`__tests__/evidence-chain-resolver.test.ts`), independent of any one pack's domain types.
- **`CapabilityResult`** (`capability-result.ts`) — the common `{ metrics, ratios, observations, evidence, signals }` shape every pack's own result type now `extends`, after verifying (not assuming) all three existing result interfaces already declared it identically.

Both are internal to `financial-intelligence/` — never exported from `index.ts`, and no Capability Pack's own result type is exported from `index.ts` either. This is a shared contract between `capabilities/*` implementations, not a new public surface.

**Applying the shared resolver surfaced a real, pre-existing evidence-chain defect in Cash Flow**, fixed alongside the refactor (permitted under "frozen except defect fixes"): `generateCashFlowEvidence()` was only ever given `cashMovements`, but both of Cash Flow's Ratios also depend on `total_current_liabilities` (a Liquidity metric, backed by `Liability` objects) — so the Liability-side `EvidenceObject`s an Observation partly derived from were silently omitted from the chain (never empty, since the Cash Flow side alone was non-empty, but incomplete). Fixed by widening the generator's last parameter to `readonly EvidenceLinkedFinancialObject[]` and passing `[...cashMovements, ...liabilities]` from the orchestrator. See `docs/98_TECHNICAL_BACKLOG.md` CF-004. Working Capital's own evidence generator was built correctly from the start, informed by this fix.

## Capability Packs

**The pattern.** A Capability Pack is one complete, real, vertical business-domain slice through the entire Financial Intelligence pipeline — Financial Object construction (or, for a pack whose Ratio needs only Metrics other packs already compute, reuse of another pack's construction — see Investment below), Metric calculators, Ratio calculators, Observation calculators, Evidence generation (via the shared `EvidenceChainResolver`), and (via the existing shared `FinancialSignalGenerator`) Signal generation, all for one business domain. Each pack lives under `capabilities/<domain>/`, owns its own calculator implementations, and exposes one `run<Domain>CapabilityPack(document, evidence)` entry function returning a `CapabilityResult`-extending type, with the same `(StructuredDocument, EvidenceObject[])` signature as `analyzeFinancialSignals()` — independently testable and independently demonstrable without touching any other pack or the frozen pipeline/contract layers. Packs are built one at a time and, once complete, are **frozen except for defect fixes** — Liquidity, Profitability, Cash Flow, Working Capital, Leverage, Efficiency, and Growth were each frozen on the next pack's approval. The recommended order — Liquidity, Profitability, Cash Flow, Working Capital, Leverage, Efficiency, Growth, Investment — is now **complete**: Investment was the eighth and final planned pack.

A pack with more than a couple of calculators per stage (Profitability's five Metric calculators, for instance) groups them into one file per stage (`profitability-metric-calculators.ts`, `-ratio-calculators.ts`, `-observation-calculators.ts`) rather than Liquidity's one-file-per-calculator layout, to avoid excessive boilerplate — both layouts are acceptable; pick whichever keeps a pack's calculator count readable.

**Cross-pack Metric reuse.** Cash Flow was the first pack whose Ratio layer needed a Metric another pack computes; Working Capital, Leverage, and Efficiency followed (Working Capital needs both `total_current_assets` and `total_current_liabilities`; Leverage needs `total_current_liabilities` merged with its own `"non_current"`-classified Liabilities; Efficiency needs `total_current_assets` merged with its own `"non_current"`-classified Assets, **plus** `total_revenue` from Profitability — the first pack to reuse Metrics/Objects from two different other packs at once). Rather than duplicating Liquidity's Asset/Liability construction (or, for Efficiency, Profitability's Revenue/Expense construction), each pack directly imports and calls the earlier pack's already-frozen, already-tested builder/calculators, merging the resulting metric(s) into their own metrics array before running their Ratio calculators — and, per the CF-004 lesson above, passing the *full* set of Financial Objects (own + reused) to their evidence generator, not only their own. Nothing in ADR-005 restricts this cross-pack reuse — it governs the *top-level* module boundary (`financial-intelligence/` as a whole exposes one entry point to *other* modules), not imports between sibling `capabilities/*/` subfolders of the same module. A pack being "independently testable" means its own tests don't depend on another pack's tests passing, not that it may not call another pack's frozen, already-tested code as a building block.

**Growth is the first pack that could not reuse another pack's Metric for its core calculation, and says so.** Revenue Growth Rate structurally needs two distinct *period-scoped* Revenue values — no existing Metric represents a single period's Revenue in isolation, since Profitability's `total_revenue` deliberately aggregates every Revenue row a document has. Rather than force a reuse that would not actually produce a correct result, Growth introduces its own Financial Object construction (`period-revenue-builder.ts`) and its own two Metrics (`current_period_revenue`/`prior_period_revenue`) — disclosed as a genuine exception to "reuse whenever possible," not a missed opportunity (`docs/98_TECHNICAL_BACKLOG.md` GR-002).

**Investment is the opposite extreme: total reuse, nothing new but the Ratio.** Return on Equity needs only `gross_profit` (Profitability) and `total_equity` (Leverage) — two Metrics two *other*, already-frozen packs already fully compute from their own already-frozen builders. Investment's `run` function calls `buildRevenueAndExpenses`, `GrossProfitCalculator`, `buildLeverageFinancialObjects`, and `TotalEquityCalculator` directly, unmodified — no new Financial Object builder, no new Metric calculator, the first pack for which this is true. Only the Ratio calculator, Observation calculator, and Evidence generator are genuinely new.

**LC-003 — a real defect in frozen code, found by a later pack's more complete fixture.** Building Leverage's fixture (the first to include both a "Total Current Liabilities" *and* a "Total Non-Current Liabilities" row in one table) surfaced a genuine bug in Liquidity's `isCurrentAssetsSubtotalLabel`/`isCurrentLiabilitiesSubtotalLabel`: `\bcurrent\b` alone also matches inside "Non-Current" (the hyphen is a non-word character, so a `\b` boundary exists immediately before "Current" there too), silently misclassifying a "Total Non-Current Liabilities" row as `"current"` and double-counting it once Leverage started constructing the genuine `"non_current"` counterpart from the same row. Fixed under "frozen except defect fixes" by explicitly excluding "non-current" labels; a dedicated regression test was added to Liquidity's own suite (`liquidity-capability-pack.test.ts`). See `docs/98_TECHNICAL_BACKLOG.md` LC-003.

No pack is wired into `analyzeFinancialSignals()` or exported from `index.ts` — assembling every pack into one production entry point is future integration work. The Financial Intelligence Orchestrator (below) is a first step toward that, but is itself internal, not public.

### Liquidity Capability Pack (complete, frozen except defect fixes)

`capabilities/liquidity/` — the first Capability Pack, covering the `liquidity` domain end to end:

- **Financial Object calculations** — [`current-asset-liability-builder.ts`](capabilities/liquidity/current-asset-liability-builder.ts): `buildCurrentAssetsAndLiabilities(document, evidence)` constructs `Asset`/`Liability` entries classified `"current"`. Groups `EvidenceObject[]` by `(tableId, column)` (reusing `evidence/financial-evidence-rules.ts`'s `groupByColumn`), keeps only columns normalized to the Ontology terms `"Asset"`/`"Liability"`, and — since "Current Asset"/"Current Liability" are not yet registered Ontology terms — recognizes a row as a *current* entry only when its label (the table's first cell in that row) matches an explicit "Total Current Assets"/"Total Current Liabilities"-shaped subtotal, a disclosed heuristic mirroring `cash_shortages`' existing "Cash" keyword exception, and explicitly excludes "Non-Current"-labeled rows (LC-003 defect fix, see below). Individual current-asset/liability line items without an explicit subtotal row are **not** summed (a stated limitation — see `docs/98_TECHNICAL_BACKLOG.md` LC-001).
- **Financial Metric calculations** — [`total-current-assets-calculator.ts`](capabilities/liquidity/total-current-assets-calculator.ts) / [`total-current-liabilities-calculator.ts`](capabilities/liquidity/total-current-liabilities-calculator.ts): sum the constructed Asset/Liability entries; Metric confidence is the average of the contributing Financial Objects' confidence, which is itself the confidence of the single `EvidenceObject` each was built from — a genuinely threaded, non-fabricated confidence chain from source document to Metric.
- **Financial Ratio calculations** — [`current-ratio-calculator.ts`](capabilities/liquidity/current-ratio-calculator.ts): Current Ratio = total_current_assets ÷ total_current_liabilities. Refuses to divide by zero; `canCalculate()` and `calculate()` agree.
- **Financial Observation generation** — [`current-ratio-below-range-calculator.ts`](capabilities/liquidity/current-ratio-below-range-calculator.ts): emits `current_ratio_below_range` only when the ratio is genuinely below `PREFERRED_CURRENT_RATIO_MINIMUM` (1.5) — a disclosed industry-standard heuristic threshold, not yet a formal, versioned Benchmark object (see `docs/98_TECHNICAL_BACKLOG.md` LC-002).
- **Financial Evidence generation** — [`liquidity-evidence-generator.ts`](capabilities/liquidity/liquidity-evidence-generator.ts): the first real implementation of the target pipeline's Observation → Evidence step. Maps liquidity Observations to `working_capital_pressure` — per [`05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md`](../../../docs/05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md) Chapter 5, that evidence type's required fields are literally "Current Asset/Liability Balances," exactly what `current_ratio` is computed from. This was one of the five previously-deferred `FinancialEvidenceType` categories with no detection logic — filled in here via the Observation-based path only (`FinancialEvidenceClassifier` remains untouched and still never produces it). `evidenceObjectIds` is resolved via the shared `EvidenceChainResolver` (`internal/capability-support/`) — the full chain (Observation → Ratio.metricIds → Metric.financialObjectIds → Asset/Liability.evidenceObjectIds) back to real `EvidenceObject` ids, honoring `FinancialEvidence`'s frozen contract rather than reinterpreting it.
- **Financial Signal generation** — reuses the existing, unmodified `FinancialSignalGenerator`. `financial-signal-rules.ts`'s `liquidity_stress` rule was extended (data only, not structurally) to also trigger on `working_capital_pressure`, per FIF Chapter 6's "Cash shortages + Working capital pressure" — this does not change `analyzeFinancialSignals()`'s behavior, since its evidence still comes solely from `FinancialEvidenceClassifier`, which never emits `working_capital_pressure`.

`liquidity-capability-pack.ts`'s `runLiquidityCapabilityPack(document, evidence)` ties all six steps together and is the pack's single entry point, tested directly in `capabilities/liquidity/__tests__/liquidity-capability-pack.test.ts`.

### Profitability Capability Pack (complete, frozen except defect fixes)

`capabilities/profitability/` — the second Capability Pack, covering the `profitability` domain end to end:

- **Financial Object calculations** — [`revenue-expense-builder.ts`](capabilities/profitability/revenue-expense-builder.ts): `buildRevenueAndExpenses(document, evidence)` constructs `Revenue` and `Expense` (classified `"cogs"`/`"operating"`) entries. Same `groupByColumn` + row-label-heuristic approach as Liquidity's builder: a Revenue row requires an explicit "Total Revenue"/"Total Sales" label (same double-counting-avoidance reasoning as Liquidity's subtotal requirement); an Operating Expense row likewise requires an explicit "Total Operating Expenses" label; a COGS row does **not** require a "total" label — a single "Cost of Goods Sold"/"Cost of Sales" line is, by convention, already the total, with no equivalent multi-line-item double-counting risk. An Expense row matching neither COGS nor Operating Expenses (e.g. Interest Expense) is not constructed at all (see `docs/98_TECHNICAL_BACKLOG.md` PC-001, which generalizes Liquidity's LC-001).
- **Financial Metric calculations** — [`profitability-metric-calculators.ts`](capabilities/profitability/profitability-metric-calculators.ts): `TotalRevenueCalculator`, `CostOfGoodsSoldCalculator`, `GrossProfitCalculator` (Revenue − COGS), `TotalOperatingExpensesCalculator`, `NetProfitCalculator` (Revenue − COGS − Operating Expenses). All five read directly from `FinancialObjectSet` — `NetProfitCalculator` does not subtract the `GrossProfitCalculator`'s output (no intra-stage calculator dependency exists in the frozen execution architecture); the two are mathematically consistent by construction, computed independently.
- **Financial Ratio calculations** — [`profitability-ratio-calculators.ts`](capabilities/profitability/profitability-ratio-calculators.ts): `GrossMarginCalculator` (gross_profit ÷ total_revenue), `NetMarginCalculator` and `OperatingMarginCalculator` (both net_profit ÷ total_revenue — currently identical values; see `docs/98_TECHNICAL_BACKLOG.md` PC-002). All three refuse to divide by zero revenue.
- **Financial Observation generation** — [`profitability-observation-calculators.ts`](capabilities/profitability/profitability-observation-calculators.ts): `GrossMarginNegativeCalculator`/`NetMarginNegativeCalculator`/`OperatingMarginNegativeCalculator`, each firing only when its ratio is genuinely below zero — a single-period, universally-defensible threshold chosen specifically to avoid Liquidity's industry-dependent-threshold problem (see `docs/98_TECHNICAL_BACKLOG.md` LC-002/PC-002). Deliberately distinct from the already-registered, still-unimplemented `gross_margin_declined`/`expense_growth_outpaced_revenue` definitions, both period-over-period trends this platform cannot yet detect (`docs/98_TECHNICAL_BACKLOG.md` PC-003).
- **Financial Evidence generation** — [`profitability-evidence-generator.ts`](capabilities/profitability/profitability-evidence-generator.ts): maps profitability Observations to the existing `margin_erosion` `FinancialEvidenceType` — already used by `FinancialEvidenceClassifier` for its own, unrelated row-trend detection; this is a second, parallel source of the same type, exactly the pattern Liquidity established for `working_capital_pressure`. `evidenceObjectIds` resolved via the shared `EvidenceChainResolver`.
- **Financial Signal generation** — reuses the existing, unmodified `FinancialSignalGenerator` **and required no rule change**: `margin_compression`'s rule already triggers on `margin_erosion` alone (registered in the original Sprint 2 Foundation milestone), so this pack's evidence reaches `margin_compression` through the registry exactly as built, with zero edits.

`profitability-capability-pack.ts`'s `runProfitabilityCapabilityPack(document, evidence)` ties all six steps together and is the pack's single entry point, tested directly in `capabilities/profitability/__tests__/profitability-capability-pack.test.ts`.

### Cash Flow Capability Pack (complete, frozen except defect fixes)

`capabilities/cash-flow/` — the third Capability Pack, covering the `cash_flow` domain end to end. Financial Objects are described in this milestone's own terms as "Cash Inflows / Cash Outflows / Operating Cash Flow" — realized as a single `CashMovement` type (already in the Financial Object Model) with a `direction: "inflow" | "outflow"` field, scoped entirely to Operating Cash Flow since this pack does not distinguish Investing/Financing sections (see `docs/98_TECHNICAL_BACKLOG.md` CF-001):

- **Financial Object calculations** — [`cash-movement-builder.ts`](capabilities/cash-flow/cash-movement-builder.ts): `buildCashMovements(document, evidence)` constructs `CashMovement` entries from columns normalized to the Ontology term `"Cash Movement"`. Unlike every prior builder, inflow/outflow classification needs **no** disclosed keyword heuristic — the sign of the observed amount decides it deterministically (positive = inflow, negative = outflow; `amount` is always stored as a non-negative magnitude, with `direction` alone carrying the sign, to avoid double-negative summation bugs). A row matching a "Net"/"Total" + "Cash" subtotal label (e.g. "Net Cash from Operating Activities") is excluded, same double-counting-avoidance reasoning as every other builder.
- **Financial Metric calculations** — [`cash-flow-metric-calculators.ts`](capabilities/cash-flow/cash-flow-metric-calculators.ts): `CashGeneratedCalculator` (sum of inflows), `CashUsedCalculator` (sum of outflows), `OperatingCashFlowCalculator` and `NetCashFlowCalculator` (both Cash Generated − Cash Used, computed independently — currently identical values for the same "no Investing/Financing split" reason Profitability's Net/Operating Margin are identical; see `docs/98_TECHNICAL_BACKLOG.md` CF-001).
- **Financial Ratio calculations** — [`cash-flow-ratio-calculators.ts`](capabilities/cash-flow/cash-flow-ratio-calculators.ts): `OperatingCashFlowRatioCalculator` (net_cash_flow ÷ total_current_liabilities) and `CashCoverageRatioCalculator` (cash_generated ÷ total_current_liabilities). **The first ratios in the registry whose formula crosses a domain boundary** — `total_current_liabilities` is a Liquidity metric, obtained by the orchestrator calling Liquidity's already-frozen builder/calculator directly (see "Cross-pack Metric reuse" above), not duplicated. "Cash Coverage Ratio" has more than one competing real-world definition; this pack's choice (Cash Generated ÷ Current Liabilities, rather than an interest-coverage-style EBIT/Interest Expense formula this platform cannot compute — no Interest Expense tracking exists, PC-001) is disclosed as one defensible variant, not presented as the only correct one (`docs/98_TECHNICAL_BACKLOG.md` CF-002).
- **Financial Observation generation** — [`cash-flow-observation-calculators.ts`](capabilities/cash-flow/cash-flow-observation-calculators.ts): `OperatingCashFlowNegativeCalculator` (fires below zero, mirroring Profitability's margin-negative pattern) and `CashCoverageRatioLowCalculator` (fires below 1.0 — gross cash generated failing to cover current liabilities even once, a defensible universal cutoff, unlike an arbitrary "preferred" ratio).
- **Financial Evidence generation** — [`cash-flow-evidence-generator.ts`](capabilities/cash-flow/cash-flow-evidence-generator.ts): maps cash_flow Observations to `negative_cash_flow` — unlike `working_capital_pressure`/`margin_erosion` (each already had an unrelated `FinancialEvidenceClassifier` rule before their respective Capability Packs), `negative_cash_flow` had **no** detection logic anywhere before this milestone. `evidenceObjectIds` now resolved via the shared `EvidenceChainResolver`, given `[...cashMovements, ...liabilities]` — widened from `cashMovements` alone as part of the CF-004 defect fix (see "Shared Internals" above).
- **Financial Signal generation** — reuses the existing `FinancialSignalGenerator`, with one new rule added: `cash_conversion_deterioration` (previously dead — one of the three signal types with no reachable trigger) now fires on `negative_cash_flow`, per FIF Chapter 6. Data-only change, `analyzeFinancialSignals()` unaffected — its evidence source never produces `negative_cash_flow`.

`cash-flow-capability-pack.ts`'s `runCashFlowCapabilityPack(document, evidence)` ties all six steps together and is the pack's single entry point, tested directly in `capabilities/cash-flow/__tests__/cash-flow-capability-pack.test.ts`.

### Working Capital Capability Pack (complete, frozen except defect fixes)

`capabilities/working-capital/` — the fourth Capability Pack, covering the `working_capital` domain end to end:

- **Financial Object calculations** — [`working-capital-component-builder.ts`](capabilities/working-capital/working-capital-component-builder.ts): `buildWorkingCapitalComponents(document, evidence)` constructs `WorkingCapitalComponent` entries (`"receivables"`, `"payables"`, `"inventory"`). Unlike every other builder, no registered Ontology term distinguishes these individually (`"Working Capital Component"`'s synonyms are just `["Working Capital Item"]`, a label real statements essentially never use) — so this builder scans the *same* Asset/Liability-normalized columns Liquidity's builder already scans, pulling out *different* rows via a disclosed row-label heuristic (`/receivable/i`, `/payable/i`, `/inventory|stock/i`, no "total" requirement needed since these are typically single line items, not aggregatable categories). A "Total Current Assets" row never matches these patterns and an "Accounts Receivable" row never matches Liquidity's "total current" pattern, so the two builders never process the same row twice. `"short_term_debt"`, the fourth `WorkingCapitalComponent.kind`, is not constructed (see `docs/98_TECHNICAL_BACKLOG.md` WC-001).
- **Financial Metric calculations** — [`working-capital-metric-calculators.ts`](capabilities/working-capital/working-capital-metric-calculators.ts): `AccountsReceivableBalanceCalculator`, `AccountsPayableBalanceCalculator`, `InventoryBalanceCalculator` — populating three definitions registered since Sprint 2 Foundation that had no calculator until now.
- **Financial Ratio calculations** — [`working-capital-ratio-calculator.ts`](capabilities/working-capital/working-capital-ratio-calculator.ts): `WorkingCapitalRatioCalculator` — (total_current_assets − total_current_liabilities) ÷ total_current_liabilities, per the already-registered definition's own description. Algebraically equal to `current_ratio − 1`, but a genuinely distinct ratio (net working capital relative to obligations), not a duplicate. The second pack (after Cash Flow) whose Ratio needs Metrics from another domain — both `total_current_assets` and `total_current_liabilities` are Liquidity's, reused directly.
- **Financial Observation generation** — [`working-capital-observation-calculator.ts`](capabilities/working-capital/working-capital-observation-calculator.ts): `WorkingCapitalRatioNegativeCalculator`, firing only when Working Capital Ratio is genuinely below zero (current liabilities exceed current assets) — the same single-period, universally-defensible "below zero" pattern as every other pack, deliberately distinct from the pre-existing, still-unimplemented `working_capital_weakened` (a period-over-period trend; PC-003).
- **Financial Evidence generation** — [`working-capital-evidence-generator.ts`](capabilities/working-capital/working-capital-evidence-generator.ts): maps working_capital Observations to `working_capital_pressure` — a **third** independent source of that type (after `FinancialEvidenceClassifier`, which never produces it, and Liquidity's generator, which does), the same established "multiple sources, one type" pattern as `margin_erosion`. The first pack built directly on the shared `EvidenceChainResolver` from day one, and correctly passes the *full* Financial Object set it draws from (`[...workingCapitalComponents, ...assets, ...liabilities]`) — informed by Cash Flow's CF-004 defect fix, not repeating it.
- **Financial Signal generation** — reuses the existing `FinancialSignalGenerator` **with zero rule changes**: `liquidity_stress`'s rule already triggers on `working_capital_pressure` (added during the Liquidity milestone), so this pack's evidence reaches it through the registry exactly as built.

`working-capital-capability-pack.ts`'s `runWorkingCapitalCapabilityPack(document, evidence)` ties all six steps together and is the pack's single entry point, tested directly in `capabilities/working-capital/__tests__/working-capital-capability-pack.test.ts`.

Unlike every prior pack, Growth's Financial Object and Metric layers are entirely its own — see "Cross-pack Metric reuse" above for why no reuse was possible here, and `docs/98_TECHNICAL_BACKLOG.md` GR-001/GR-002 for the two disclosed architectural decisions this required:

- **Financial Object calculations** — [`period-revenue-builder.ts`](capabilities/growth/period-revenue-builder.ts): `buildPeriodRevenueSequence(document, evidence)` constructs exactly two `Revenue` entries per qualifying Revenue-normalized column, tagged `periodSequence: "prior"`/`"current"` — the **last two rows, in row order**, excluding any "Total Revenue"/"Total Sales" subtotal row. This is a genuinely different selection from Profitability's `buildRevenueAndExpenses` (which keeps only the aggregate subtotal row) — the same "same column, different rows" precedent Working Capital's builder established relative to Liquidity's, not a duplicate. The row-sequence-as-period-proxy assumption is not new: it mirrors the frozen `FinancialEvidenceClassifier`'s own `revenue_growth` trend detector (`evidence/financial-evidence-rules.ts`'s `detectTrend`), which has always treated successive rows in one column as a document's implicit time axis. No real `Period` (date-boundary) value is ever constructed — see GR-001.
- **Financial Metric calculations** — [`growth-metric-calculators.ts`](capabilities/growth/growth-metric-calculators.ts): `CurrentPeriodRevenueCalculator`/`PriorPeriodRevenueCalculator`, each filtering `context.financialObjects.revenue` by its `periodSequence` tag and summing (mirrors Profitability's `cogsOf`/`operatingExpensesOf` filter-by-field shape, applied to `Revenue.periodSequence` instead of `Expense.category`). Populate the **first two new Metric definitions** any Capability Pack has introduced (GR-002).
- **Financial Ratio calculations** — [`revenue-growth-rate-calculator.ts`](capabilities/growth/revenue-growth-rate-calculator.ts): `RevenueGrowthRateCalculator` — (current_period_revenue − prior_period_revenue) ÷ prior_period_revenue, per the already-registered `revenue_growth_rate` definition, whose `requiredMetricDefinitionIds` this milestone corrected to match (GR-002). Refuses to divide by zero prior-period revenue.
- **Financial Observation generation** — [`revenue-growth-negative-calculator.ts`](capabilities/growth/revenue-growth-negative-calculator.ts): `RevenueGrowthNegativeCalculator`, firing only when Revenue Growth Rate is genuinely negative — the same single-period, universally-defensible "below zero" pattern as every other pack's "negative" Observation, deliberately distinct from the pre-existing, still-unimplemented `revenue_growth_slowed` (a genuine three-period deceleration trend, still blocked by the same period-tracking gap GR-001 discloses).
- **Financial Evidence generation** — [`growth-evidence-generator.ts`](capabilities/growth/growth-evidence-generator.ts): maps growth Observations to `revenue_growth` — the **third** independent source of that type (after the frozen `FinancialEvidenceClassifier`'s own trend detector and Efficiency's generator), and unlike Efficiency's EFF-001 mapping, a **clean** fit rather than a disclosed compromise: per FIF Chapter 5's own convention, direction (growth or decline) belongs in `basis`, not the type itself — exactly as `detectTrend`'s own doc comment already states.
- **Financial Signal generation — a Knowledge Rule change disclosure, per this milestone's explicit instruction.** No rule change was needed or made: `revenue_instability`'s rule already triggers on `revenue_growth` alone (extended to version `1.1.0` during the Efficiency milestone, EFF-002), so Growth's evidence reaches it through the existing, unmodified `FinancialSignalRuleRegistry`. This absence-of-change is stated explicitly, not left implicit, satisfying "any modification to `FinancialSignalGenerator` rules must be documented as a Knowledge Rule change" by confirming there is none to document this milestone.

`growth-capability-pack.ts`'s `runGrowthCapabilityPack(document, evidence)` ties all six steps together and is the pack's single entry point, tested directly in `capabilities/growth/__tests__/growth-capability-pack.test.ts`.

## Financial Intelligence Orchestrator (`orchestration/`, internal)

Established between the Working Capital and Leverage milestones — the first component that runs *every* registered Capability Pack against one document and combines their output, rather than each pack being called independently. Internal to `financial-intelligence/`: not exported from `index.ts`, not wired into `analyzeFinancialSignals()`. This milestone builds the orchestration mechanism only — it introduces no Finding, Root Cause, Recommendation, or Report; `signals` remains its result's terminal field, exactly as every underlying Capability Pack's own result already stops there.

- **`FinancialAnalysisResult`** (`financial-analysis-result.ts`) — the unified output: `documentId`, `packsExecuted` (which packs ran, in order), and the five aggregated, deduplicated `CapabilityResult` fields.
- **`CapabilityPackRegistry`** (`capability-pack-registry.ts`) — a `register()`/`get()`/`all()` registry of `CapabilityPackDescriptor`s (`{ id, name, run }`), the same data-driven shape as every other registry in this module. `run` is typed against the shared `CapabilityResult` base, not any one pack's richer own result type — the orchestrator never needs a pack's raw Financial Objects.
- **`createDefaultCapabilityPackRegistry()`** (`default-capability-pack-registry.ts`) — the one file that imports every pack's entry function at once, registering all eight in the documented "recommended order" (Liquidity, Profitability, Cash Flow, Working Capital, Leverage, Efficiency, Growth, Investment) — now complete, per the recommended order's own final entry. A genuinely new future pack (outside the original eight) would still mean one more `register()` call here; nothing else in `orchestration/` changes. Adding Efficiency's, Growth's, and Investment's `register()` calls here is, per this component's own designated purpose, not treated as "modifying the Orchestrator" — `CapabilityPackRegistry` and `FinancialIntelligenceOrchestrator` themselves are untouched.
- **`FinancialIntelligenceOrchestrator`** (`financial-intelligence-orchestrator.ts`) — `analyze(document, evidence)` runs every pack in the registry's fixed registration order and aggregates. **Duplicate handling**: deduplicates by `id` — since every id in this module is content-derived (`deriveCompositeId`, never random), two records sharing an id are the same record by construction. Applied uniformly to all five result arrays, not only Evidence/Signal: e.g. `total_current_liabilities` is independently computed by Liquidity directly and reused internally by Cash Flow, Working Capital, and Leverage — naively aggregating all five packs' results would show that one Metric up to four times; deduplication collapses it to one. **Deliberately does not attempt semantic consolidation** — two *different* `liquidity_stress` Signals (same type, different triggering evidence, different ids, both genuinely produced by different packs) are kept as two separate, honestly distinct records, not merged into one re-corroborated signal. That is a real feature with its own judgment calls (recomputing confidence, representing multi-pack provenance) explicitly out of this milestone's "Implement only" scope — see `docs/98_TECHNICAL_BACKLOG.md` FIO-002.
- **Deterministic, not efficient** — given identical `(document, evidence)` input and an identical registry, `analyze()` always returns byte-for-byte identical output (no randomness, no unordered iteration; every underlying pack was already independently verified deterministic). It is **not** optimized: because each pack independently reconstructs Financial Objects from raw `EvidenceObject[]` (e.g. `buildCurrentAssetsAndLiabilities` runs once inside Liquidity's own pack and again inside Cash Flow's, Working Capital's, and Leverage's cross-pack reuse), the orchestrator recomputes the same pure, deterministic construction multiple times per `analyze()` call — a disclosed, accepted tradeoff, not a correctness bug (see `docs/98_TECHNICAL_BACKLOG.md` FIO-001).

Directly unit-tested with test-double packs (`orchestration/__tests__/financial-intelligence-orchestrator.test.ts`) for the aggregation/dedup/determinism mechanics in isolation, and end-to-end with the real default registry against a real multi-table fixture proving genuine cross-pack Metric deduplication and genuine same-type-different-id Evidence/Signal preservation.

## Financial Evidence Model

`shared/contracts/financial-evidence.ts` defines the complete `FinancialEvidenceType` union — all fifteen categories from [`05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md`](../../../docs/05_FINANCIAL_INTELLIGENCE_FRAMEWORK.md) Chapter 5.

`evidence/financial-evidence-classifier.ts` implements real, deterministic detection for **ten of the fifteen** categories, operating directly on `EvidenceObject[]` (per the "current implementation status" note above, not yet on `FinancialRatio[]`): `revenue_growth`, `cost_escalation`, `debt_growth` (trend detection across a table column normalized to the corresponding Ontology term), `margin_erosion` (a composite of correlated Revenue and Expense trends in the same table), `duplicate_payments` (identical amounts within a short row span — deliberately NOT ontology-gated, since a duplicate payment is meaningful in any amount column), `cash_shortages` (negative values in a cash-context column), `missing_reconciliations` (a table's final row not matching the sum of the rows above it — also deliberately not ontology-gated), and `revenue_concentration` / `customer_dependency` / `supplier_dependency` (a single named entity accounting for a large share of a column's total).

**Three categories remain complete in the type system but have no rule wired in**: `inventory_accumulation`, `receivable_ageing`, `payable_ageing` — see code comments in `financial-evidence-rules.ts` for the specific reason each was deferred rather than implemented shallowly. `negative_cash_flow` had no detection logic anywhere before the Cash Flow Capability Pack milestone. `working_capital_pressure` now has **three** independent sources (`FinancialEvidenceClassifier`, which never produces it; Liquidity's generator, from `current_ratio_below_range`; Working Capital's generator, from `working_capital_ratio_negative`); `debt_growth` has **two**; `margin_erosion` now has **three** (its own pre-existing `FinancialEvidenceClassifier` trend detector, plus Profitability's generator, plus, as of this milestone, Investment's generator — a disclosed, imperfect mapping, INV-001); `revenue_growth` has **three** (its own pre-existing `FinancialEvidenceClassifier` trend detector, plus Efficiency's generator — a disclosed, imperfect mapping, EFF-001 — plus Growth's generator — a clean, FIF-convention-grounded mapping, not a compromise). All eight Capability Pack evidence generators (`capabilities/liquidity/`, `capabilities/profitability/`, `capabilities/cash-flow/`, `capabilities/working-capital/`, `capabilities/leverage/`, `capabilities/efficiency/`, `capabilities/growth/`, `capabilities/investment/`) run parallel to and independent of `FinancialEvidenceClassifier`, which is unchanged throughout, and all eight now share the same `EvidenceChainResolver` (`internal/capability-support/`) rather than each maintaining a private copy.

## Financial Signal Model

`shared/contracts/financial-signal.ts` defines the complete `FinancialSignalType` union — all ten categories from Chapter 6.

`signals/financial-signal-generator.ts`, driven by a data-driven `FinancialSignalRuleRegistry`, implements **eight of the ten** signal types: `liquidity_stress`, `margin_compression`, `operating_cost_inflation`, `revenue_instability`, `cash_conversion_deterioration`, `over_reliance_on_debt`, `supplier_concentration`, `profit_quality_concerns`. The remaining two (`inventory_build_up`, `working_capital_deterioration`) have no registered rule. `liquidity_stress`'s rule was extended (data only) to trigger on `cash_shortages` **or** `working_capital_pressure` (rule version bumped to `1.1.0`), per FIF Chapter 6, during the Liquidity milestone — and now, without any further rule change, also fires from Working Capital's independently-generated `working_capital_pressure` evidence, since the rule triggers on the *type*, not its source. `margin_compression` and `over_reliance_on_debt` needed **no change at all** for Profitability/Leverage respectively — both already triggered on `margin_erosion`/`debt_growth` alone. `cash_conversion_deterioration` is a **new** rule, added during the Cash Flow milestone, triggering on `negative_cash_flow` (per FIF Chapter 6; `receivable_ageing`, its documented co-trigger, still has no detection logic, so this rule is single-trigger for now).

> **Architectural note, prominently disclosed (EFF-002): the Efficiency milestone's `revenue_instability` rule extension is the first signal-rule change in this project's history to genuinely widen `analyzeFinancialSignals()`'s own reachable output.** `revenue_instability`'s rule was extended (data only, version bumped to `1.1.0`) to also trigger on `revenue_growth` alone — grounded directly in FIF Chapter 6's own documented trigger table ("Erratic Revenue growth pattern, or Revenue concentration + Customer dependency"), a pre-existing gap between FIF's own text and the implemented rule, present since Sprint 2 Foundation and independent of Efficiency's own domain (Efficiency's `asset_turnover_zero` Observation merely surfaced it). Every *other* rule change documented in this section — `liquidity_stress` + `working_capital_pressure`, `cash_conversion_deterioration` + `negative_cash_flow` — added a trigger type that was reachable *only* through its Capability Pack's own new Observation-based evidence generator, so `analyzeFinancialSignals()` (whose evidence comes solely from the frozen `FinancialEvidenceClassifier`, never from a Capability Pack) could never actually reach any of them; those changes were genuinely inert from `analyzeFinancialSignals()`'s point of view. `revenue_growth` breaks that pattern: `FinancialEvidenceClassifier` has produced it directly, via its own unrelated trend detector, since Sprint 2 Foundation. So this one rule change means a document with erratic revenue growth alone — with **no** Capability Pack, Orchestrator, or `EvidenceObject`-level Efficiency logic ever invoked — can now produce a `revenue_instability` signal through `analyzeFinancialSignals()` where it could not before. This was a deliberate, considered decision, not an oversight: the change is purely additive (no previously-reachable evidence-to-signal path was removed or altered), it closes a genuine and longstanding documentation/implementation gap, and it was verified empirically rather than assumed — `__tests__/real-pipeline-integration.test.ts` gained a new explicit assertion proving a real parsed document now produces a `revenue_instability` signal via `analyzeFinancialSignals()` directly, with the full suite green both before and after the change. `FinancialSignalRuleRegistry`'s mechanism, `FinancialEvidenceClassifier`, and `analyzeFinancialSignals()`'s own code are all completely unmodified — only the data-table content of one rule changed. See `docs/98_TECHNICAL_BACKLOG.md` EFF-002 for the full account.

None of these changes altered `FinancialSignalRuleRegistry`'s mechanism.

> **Knowledge Rule change disclosure, Growth Capability Pack milestone.** Per that milestone's explicit instruction ("any modification to `FinancialSignalGenerator` rules must be documented as a Knowledge Rule change, with rationale and test coverage"): **no rule was modified.** Growth's evidence generator (`capabilities/growth/growth-evidence-generator.ts`) maps to the existing `revenue_growth` `FinancialEvidenceType`, and `revenue_instability`'s rule already covers that type (via the `1.1.0` extension made during Efficiency, EFF-002) — so Growth's evidence reaches `revenue_instability` through the registry exactly as it already stood, with zero edits to `financial-signal-rules.ts`. This absence-of-change is recorded explicitly here (satisfying the disclosure instruction by confirming there is nothing to disclose), and is exercised by `capabilities/growth/__tests__/growth-capability-pack.test.ts`'s own end-to-end test asserting a real `revenue_instability` signal fires from Growth's output.

> **Knowledge Rule change disclosure, Investment Capability Pack milestone.** Same instruction, same outcome: **no rule was modified.** Investment's evidence generator (`capabilities/investment/investment-evidence-generator.ts`) maps to the existing `margin_erosion` `FinancialEvidenceType`, and `margin_compression`'s rule has triggered on `margin_erosion` alone since Sprint 2 Foundation — zero edits to `financial-signal-rules.ts` were needed. Exercised by `capabilities/investment/__tests__/investment-capability-pack.test.ts`'s own end-to-end test asserting a real `margin_compression` signal fires from Investment's output.

## Confidence

Every `FinancialEvidence` and `FinancialSignal` carries a `Confidence` value object, never a bare number. Signal confidence is the average of its triggering evidence's confidence plus a small, documented corroboration bonus, capped at 0.9. `FinancialMetric`/`FinancialRatio`/`FinancialObservation` carry `Confidence` too — for all eight completed-pack domains (liquidity, profitability, cash-flow, working-capital, leverage, efficiency, growth, investment) this is now a genuinely threaded, non-fabricated value (traced from the constructed Financial Object's `EvidenceObject`-derived confidence, averaged upward through each stage); every other, un-built domain still has no calculators to populate it.

## What this module does not do (by design)

No diagnostics system (unlike `document-parser/`'s `ParserDiagnostic`) — not requested, not added speculatively. No Findings, Root Causes, Recommendations, or Reports — those require `brain/` (ADR-006), even for all eight completed Capability Packs and the Orchestrator that runs them together, whose aggregated signals remain the terminal output. No Operational Correlation — that is `correlation/`'s job. No Metric/Ratio/Observation formula outside the eight completed Capability Packs' real calculators — every other registered definition still has none. Observations remain deliberately non-diagnostic by construction (see "Financial Observations" above) — `current_ratio_below_range`/`net_margin_negative`/`operating_cash_flow_negative`/`working_capital_ratio_negative`/`debt_to_equity_negative`/`asset_turnover_zero`/`revenue_growth_negative`/`return_on_equity_negative` state facts, never a cause. No pack, and no `FinancialAnalysisResult`, is wired into `analyzeFinancialSignals()` or exported from `index.ts` — each Capability Pack remains its own self-contained, directly-callable entry point, and the Orchestrator is a separate, also-internal way to call all of them at once; neither changes what `analyzeFinancialSignals()` itself does directly (though, per the EFF-002 note above, one data-table rule extension motivated by Efficiency's domain does genuinely widen what `analyzeFinancialSignals()` can now produce from its own pre-existing evidence source — a disclosed, additive exception, not a rewiring; Growth and Investment each made no further rule change at all, per the Knowledge Rule disclosures above). Liquidity, Profitability, Cash Flow, Working Capital, Leverage, Efficiency, and Growth are frozen except for defect fixes, per their own approvals; so is `internal/capability-support/`, `CapabilityPackRegistry`, `FinancialIntelligenceOrchestrator`, and `FinancialAnalysisResult`. Investment remains open pending its own approval. Per this milestone's own instruction, the next work is a **Financial Intelligence Validation milestone** (not Findings) — see the top status line.
